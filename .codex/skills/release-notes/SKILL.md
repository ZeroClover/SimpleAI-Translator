# 版本更新说明

让用户快速知道本次更新解决了什么、自己是否受影响、是否需要操作。更新说明不是提交日志，也不是开发总结。

## 从真实变化出发

- 确认目标版本和上次发布的标签，读取两者之间的 diff、相关代码和验证结果。提交标题只用于找线索，不能直接作为更新说明。
- 合并同一用户问题背后的多次提交；不把重构、测试、CI、Skill 或发布准备单独写成产品功能。
- 只写已经实现的用户可见变化。限制和必要操作要直接说明；不要声称未经验证的平台或场景已修复。

## 写法

- 默认用简体中文；用户指定语言时遵循用户要求。
- 每条说明一个变化，先写具体问题或新行为。通常一两句话就够，条数由实际变化决定，不凑数。
- 用用户在界面上认识的名称。实现细节只有影响用户选择或操作时才保留。
- 不写“全面升级”“体验更佳”“进一步优化”“修复若干问题”等无法核对的空话；不逐条罗列提交、文件名、函数名、依赖版本或工作过程。
- 修复说明交代触发条件和解决的问题。新功能说明交代能做什么。行为改变说明交代变化及必要操作。

例子：

- 不写：优化更新器布局，调整 flex、border 和 overflow，完善相关测试。
- 改写：修复更新说明较长时，版本提示和开头内容被遮住、滚动到顶部仍无法查看的问题。

## 本仓库的格式与发布链路

- 将定稿保存到 `docs/releases/<version>.md`。
- 正文只用平铺的 `- ` 列表，每条写在一个物理行内，让客户端自动折行。不要在正文重复版本号、日期、发布标题、开场白或结束语。
- 常规说明不使用表格、图片、HTML、嵌套列表或代码块。正文足够短时不要加分类标题。版本号已由 GitHub Release 标题和更新器版本提示显示。
- 更新器使用 CommonMark 渲染。不要手工添加 `■` 等显示符号，也不要把字符串中的换行写成字面的 `\n`。
- `.github/workflows/release.yaml` 将 annotated tag 的说明写入 GitHub Release，再复制 Release 正文到 `latest.json.notes`。三处内容应一致（忽略末尾空行）。只编辑 GitHub Release 不会自动重建已经上传的 `latest.json`。
- `scripts/release.py` 接受明确的版本号和审核后的说明文件，不再自动拼接提交记录。仅在发布已获授权且验证完成、工作区干净时运行：`python3 scripts/release.py <version> docs/releases/<version>.md`。它会创建并推送标签，从而触发发布工作流；起草说明本身不代表获准发布。
- 推送失败后先检查本地和远端标签及发布状态，不重复创建标签、不强制覆盖已发布版本。
- CI 从标签设置构建版本；准备版本时同时核对 `package.json`、`src-tauri/tauri.conf.json` 和 `Makefile` 的默认版本。

## 交付前核对

逐条检查：用户能否理解具体变化，是否有代码或验证证据，是否重复、夸大或遗漏必要操作。删除不能回答这些问题的句子。

涉及更新器展示时，使用真实更新说明与较长说明检查默认窗口和较窄窗口：顶部版本提示可见，首尾条目都能滚达，列表不重复符号，按钮不遮挡正文。已发布时还要读取 Release 正文与下载的 `latest.json.notes` 核对；未发布时明确称为“准备完成”，不要称为“已发布”。
